**course-agnostic working principles** (how Claude operates here, reusable for any course) and the
**per-semester working state** (namespaced `s1…` / `s2…`), for the course(s) currently hosted (the
Diploma Cloud & Cyber: S1 Cloud, S2 Cyber). "Principles, not state" — see

## Working principles (how Claude operates here)
- [one course-agnostic mechanism](one_course_agnostic_mechanism.md) — **the single most important factor:** exactly ONE mechanism per artefact type across all clusters + future courses (one source of truth, one engine, one process); unify first-built/legacy paths onto it, never fork; a capability gap becomes a feature of the one engine; reproduce→validate→adopt before retiring the old path.
- [memory = principles not state](memory_principles_not_state.md) — record durable decisions/rationale (the non-derivable WHY); never repo-derivable ephemeral state (paths, commits, "what's built") — it goes stale on creation.
- [record current-state only](feedback_process_docs_current_only.md) — record things as they ARE, not how they used to be, in everything (docs, memory, status notes): current method only, no abandoned-path archaeology; git holds it.
- [current practice, not policy](feedback_current_practice_not_policy.md) — never write our own choices up as decided/locked/canonical/never/must; they are the current approach, open to evolution. Sole exception: a constraint we have no capability to change (state that firmly).
- [write deliverables at final confidence](feedback_deliverables_final_confidence.md) — author docs as if open dependencies were done; track the dependency in MEMORY, never as an in-text "draft pending X" hedge (avoids redoing the doc just to strip caveats).
- [suggest commits, don't auto-commit](feedback_suggest_commits.md) — when a commit seems appropriate, suggest it's a good time and wait for confirmation; never auto-commit (memory is version-controlled + syncs across machines).
- [never push a website repo](feedback_never_push_website_repo.md) — committing a website repo is fine; **pushing** it triggers a CD redeploy of the live site, so leave that to the human. Pushing umbrella/content is fine even when it carries other sessions' commits — don't flag those.
- [one step at a time](feedback_one_step_at_a_time.md) — for hands-on interactive walk-throughs (AWS console, lab setup), give ONE step then wait for what he sees; don't front-load 10 steps.
- [minimal hedging in live troubleshooting](feedback_minimal_hedging_live_troubleshooting.md) — during live console troubleshooting, answer directly, skip stacked caveats/warnings; save precision for written deliverables.
- [draft naming pragmatism](feedback_draft_naming_pragmatism.md) — during drafts, don't fuss over file naming; defer naming discipline to delivery-ready versions.
- [verify change impact](feedback_verify_change_impact.md) — before side-effecting changes (esp. running file-writing generators), verify where output lands + `git status` what got staged; a "helpful" regenerate once created a phantom nested sub-repo and committed it.
- [audit generated docs via the .py builders](feedback_audit_generated_docs.md) — a cross-cutting content sweep must grep the `.py` builders (course generators under the **content repo** `scripts/`; the shared engine helpers under the **umbrella** `scripts/`) — instruments are generated `.docx`, decks `.pptx`, so you can't grep the binaries; edit the builder, regenerate with the **umbrella** `scripts/.venv`, verify the regenerated text. A `.md`/`.yaml`-only grep silently misses most deliverables.
- [materials own the failure](feedback_materials_own_the_failure.md) — someone stuck with the run sheet + lab pack in front of them means a **pack defect** or **insufficient detail**, never student error. Applies to the mechanical path only; struggling to *decide* something is the assessment working.
- [worksheet over template](feedback_worksheet_over_template.md) — everything the student produces is captured in the assessment **worksheet**; a separate fillable template only where a UoC requirement explicitly demands one (quote the AC). Exemplars follow templates — none survives without a student submittable. Format standard: `docs/assessment-workbook-format.md`.
- [mark the UoC intent, not the invented settings](feedback_mark_uoc_intent_not_invented_settings.md) — we invent specific values so a task is doable; they are context. Per setting ask "if this were wrong, would the item still be evidenced?" Every element carries `Evidences:` **and** `Satisfactory when`. Companion rule: scaffold the process, never the finding.
- [assessments freeze per delivery cycle](feedback_finalised_assessments_change_control.md) — institutional review PASS freezes instruments **for that delivery** (warn before touching); **delivering spends the approval** → they reopen for a feedback-driven improvement pass, edited **in place in the generators**; the next human review re-freezes for the next intake. Check the cluster entry for which phase. S1-CL1: delivered, **open**.
